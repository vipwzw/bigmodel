## 0. 先建立全局账本：训练大模型到底在算什么

### 0.1 训练计算量：FLOPs ≈ 6ND

一个参数量 N 的 Transformer，每个 token 的前向 + 反向约需 **6N 次浮点运算**（前向 2N、
反向 4N；注意力项在短序列下可忽略）。训练 D 个 token 的总计算量：

```
C ≈ 6 · N · D   （FLOPs）
```

本课 Stage 4 的自研训练器用 `flops_per_token()` 显式算了这个量（含注意力项），实测：

| 档位 | 参数量 N | 每 token FLOPs | 训练 token 数 D | 理论计算量 C | 实测耗时 | 实测有效算力 |
|---|---|---|---|---|---|---|
| S | 16,913,280 | 115.6 M | 2,002,944 | 231.6 TFLOPs | 100.0 s | **2.32 TFLOP/s** |
| M | 41,689,600 | 287.9 M | 1,001,472 | 288.3 TFLOPs | 140.7 s | **2.05 TFLOP/s** |
| L | 110,119,680 | 774.0 M | 507,904 | 393.1 TFLOPs | 173.3 s | **2.27 TFLOP/s** |

Stage 1 用 4096³ 矩阵乘测得本机 bf16 峰值约 **6.15 TFLOP/s**（MLX 6.18）。所以训练的有效利用率
约为 **33%–38%**。剩下 60% 以上花在哪：优化器更新、梯度归约、attention 的 softmax、显存读写、
数据搬运、以及 MPS 后端算子效率——这就是为什么"矩阵乘峰值"永远不能直接当成训练速度。

> **这一条解释了整门课的预算设计**：单机算力有限，所以 Stage 4 的 sanity 档只给 S/M/L 分别
> 2M / 1M / 0.5M token，而不是"训到收敛"。

### 0.2 数据预算：tokens per parameter

Chinchilla 缩放律的经验结论是：**计算最优时，每个参数约配 20 个 token**（N≈D/20）。
对照本课实际：

| 档位 | 参数量 | sanity token | tokens/param | standard 预算 | tokens/param |
|---|---|---|---|---|---|
| S | 16.9M | 2.00M | **0.118** | 100M | 5.9 |
| M | 41.7M | 1.00M | **0.024** | 120M | 2.9 |
| L | 110.1M | 0.51M | **0.0046** | 80M | 0.73 |

**结论**：sanity 档的模型是"严重欠训练"的（比 Chinchilla 最优少 100–4000 倍 token），
standard 档也只是接近最优量级的下限。这直接解释了 Stage 7 里困惑度非常高：
**模型不是"训练失败"，而是"没喂够数据"**。课程目的是把链路跑通、把机制讲清楚，
不是在 Mac 上复现可用大模型。

### 0.3 损失、困惑度与"学会了多少"

语言模型用交叉熵（cross-entropy, CE）训练：

```
loss = - (1/T) Σ log P(x_t | x_<t)
PPL  = exp(loss)
```

- loss 是"平均每个 token 的惊讶程度"（nats）；
- PPL 是"模型平均在多少个候选 token 之间犹豫"。

随机初始化时接近均匀分布，loss ≈ ln(词表大小)：16k 词表 → 9.70，32k → 10.40。
实测 Stage 4 收敛到 6.9–8.2，说明模型确实学到了结构：

| 档位 | 词表 | 随机基线 ln(V) | 实测 val loss | 降低 | 实测 PPL |
|---|---|---|---|---|---|
| S | 16,384 | 9.70 | 6.897 | 2.80 nats | ≈ 990 |
| M | 32,768 | 10.40 | 7.924 | 2.48 nats | ≈ 2,760 |
| L | 32,768 | 10.40 | 8.192 | 2.21 nats | ≈ 3,600 |

> 注意：**不同词表的 PPL 不可直接比较**（M/L 的 32k 词表天然 PPL 更高）。这是评测的经典陷阱，
> 也是 Stage 7 文档强调"同预算才能横比"的原因。

### 0.4 显存账：训练时显存花在哪

对 N 参数、AdamW 全参训练（混合精度 + fp32 主权重/优化器状态），显存大致：

```
params(bf16) 2N + grads(bf16) 2N + fp32 master 4N + Adam(m,v) 8N ≈ 16N 字节
```

1.1 亿参数的 L 档 ≈ 1.8 GB 状态 + 激活。实测 L 档峰值 4.26 GB、M 档 5.29 GB，
**48 GB 内存完全不是瓶颈**——再次印证：单机的约束是算力/时间，不是显存。
（LoRA 微调时只训练少量参数，但 0.6B fp32 权重 + 激活仍实测峰值 ~21 GB，见 Stage 5。）

## 1. Stage 1 原理：为什么要先测"加速器与精度"

### 1.1 机制

训练速度由三件事决定：**芯片算力**（TOPS/TFLOPs）、**内存带宽**、**软件栈效率**。
不同精度（fp32/fp16/bf16）在硬件上的吞吐完全不同；Apple Silicon 的 GPU 通过 Metal/MPS
暴露给 PyTorch，或通过 Apple 自研的 MLX 框架使用。

- **统一内存**：CPU/GPU 共享同一块物理内存，不需要显存拷贝，但带宽低于高端独显 HBM
  （M4 Pro 约 273 GB/s）。
- **bf16 混合精度**：前向/反向用 bf16（8 位指数 + 8 位尾数，动态范围大、不容易溢出），
  权重/优化器状态保留 fp32 副本。这是大模型训练的标准做法。
- **性能基线的意义**：在跑任何训练之前，先知道本机"顶格"是多少，后续任何 tokens/s
  都能换算成利用率（MFU），也才能做时间预算。

### 1.2 我们的实测与它说明的事

| 测量 | 实测值 | 含义 |
|---|---|---|
| 4096³ 矩阵乘（bf16） | MPS **6,153 GFLOPS** / MLX 6,180 GFLOPS | 本机算力的"天花板"参考 |
| S 档训练（17M 参数，2×512） | **19,062 tokens/s**，峰值 1.19 GB | 小模型接近计算效率上限 |
| M 档训练（42M 参数，2×768） | 9,088 tokens/s，峰值 3.23 GB | 参数量↑，tokens/s 近似反比下降 |
| L 档训练（110M 参数，1×1024） | 3,517 tokens/s，峰值 4.54 GB | 同左 |

用这些吞吐反推 Stage 4 的 standard 预算耗时：100M token → **1.46 h**；120M → 3.67 h；
80M → 6.32 h——与 design 里"1–2 / 2–4 / 3–6 小时"的估计吻合。**这就是"用基线校准预算"的原理**：
`时间 = token 数 / 实测吞吐`，不靠猜。

### 1.3 原理验证：从 tokens/s 反推 FLOPs 利用率

Stage 1 的 S 档吞吐 19,062 tokens/s × 115.6 MFLOPs/token ≈ **2.2 TFLOP/s**，和 Stage 4
实测有效算力 2.32 TFLOP/s 一致（差在 batch/序列长度不同）。两个独立阶段互相印证，
说明 `6ND` 这个公式在本课规模下是可靠的。

## 2. Stage 2 原理：数据决定上限

### 2.1 机制

语言模型学的是**训练数据的概率分布**。数据问题会直接变成模型问题：

- **重复数据**：同一个样本出现多次，模型会"背答案"而不是学规律，并抬高评测分数（数据泄漏）；
- **低质数据**：乱码、模板文、超短文本会把分布拉向垃圾区域；
- **数据规模**：token 数不足 → 欠训练（见 0.2 的 tokens/param）。

所以工业界数据管线都是：**获取 → 校验 → 规范化 → 过滤 → 去重 → 数据卡**。

### 2.2 去重的数学：MinHash / LSH

精确重复用哈希（sha1）即可。近似重复常用 Jaccard 相似度：

```
J(A,B) = |A ∩ B| / |A ∪ B|        （A、B 是文本的 shingle 集合）
```

对每篇文档算 MinHash 签名（k 个随机置换下 shingle 哈希的最小值），签名中相同位置的比例
是 Jaccard 的无偏估计。再用 LSH 分桶把"可能相似"的候选对筛出来，避免 O(n²) 全量比较。
本课实现：5-gram shingle + 64 个置换 + 16 个 band，Jaccard ≥ 0.8 判为重复。

### 2.3 实测

| 数据集 | 输入文档 | 保留 | 丢弃原因 | 近似去重 | 保留字符 |
|---|---|---|---|---|---|
| 中文维基 | 20,000 | 19,896 | 1 篇低唯一字符率 | **103 篇（0.52%）** | 14,938,037 |
| TinyStories | 3,000 | 2,955 | 45 篇过短/符号过多 | 0 | 2,493,373 |

**用原理读数据**：维基百科质量高、去重率低（0.52% 主要是模板化条目）；TinyStories 简单重复，
但总量小且故事独立。14.94M 字符 ÷ 1.464 字符/token（Stage 3 实测）≈ **10.2M token**；
sanity 档只打包了 4M token（约 39%），足够验证流程。

## 3. Stage 3 原理：分词器与序列打包

### 3.1 BPE 分词器：词表大小是一笔账

Byte-level BPE 从 256 个字节开始，反复合并语料中最高频的相邻 token 对，直到达到目标词表。
它决定了"1 个 token 平均对应多少字符"（压缩率）。

- 词表越大 → 压缩率越高（同样文本 token 更少）→ 训练同样字符数更省算力；
- 但 embedding 层参数量 = `vocab_size × hidden_dim`，词表越大 embedding 越贵。

实测：

| 分词器 | 词表 | 字符/token | 每文档 token p50 | 未知 token |
|---|---|---|---|---|
| bpe_16384 | 16,384 | 1.464 | 305 | 0% |
| bpe_32768 | 32,768 | 1.621 | 270 | 0% |

代入三个模型档位（embedding 均与输出层共享权重，只算一次）：

| 档位 | 词表×维度 | embedding 参数 | 总参数 | 占比 |
|---|---|---|---|---|
| S | 16,384×384 | 6.29M | 16.91M | **37.2%** |
| M | 32,768×512 | 16.78M | 41.69M | **40.2%** |
| L | 32,768×768 | 25.17M | 110.12M | **22.9%** |

**原理结论**：小模型里 embedding 可能占三分之一以上参数；词表选择是"压缩率 vs 参数预算"
的权衡，不是越大越好。

### 3.2 序列打包（packing）：为什么需要掩码

语言模型训练希望每个序列都是固定长度（如 1024）以填满硬件。但文档长短不一：
短文档单独成序列会浪费大量填充位。**Packing** 把多篇文档的 token 直接拼接、切成长度为
`block_size` 的序列，把利用率提到接近 100%。

代价与原理：

- **填充/损失掩码（loss mask）**：拼接后末尾不足的位置要屏蔽，否则模型会去学 pad；
- **跨文档注意力污染（segment mask）**：一条序列可能包含多篇文档，如果允许全局因果注意力，
  后一篇文档的 token 会"看到"前一篇文档的内容——训练目标被污染。做法是记录
  `segment_ids`，构造"同段 + causal"的注意力掩码。

实测（中文 packed train，4M token）：

| 指标 | 实测 |
|---|---|
| 序列数（block=1024） | 3,907 |
| 平均每序列包含文档数 | **3.13 篇** |
| 跨文档序列占比 | **82.9%** |

**原理结论**：82.9% 的序列跨文档，说明**段掩码不是可选优化，而是正确性问题**。
Stage 3 的 `segment_attention_bias()` 就是为它准备的（Stage 4 的预训练为追求吞吐使用纯 causal，
文档里明确标注这个取舍；严格复现时应启用段掩码）。

### 3.3 数据划分：为什么要先分文档再打包

如果先拼 token 流再随机切分，同一篇文档可能同时出现在 train 和 val（泄漏）。
本课先在**文档级**按种子打乱划分（train/val/test = 98%/1%/1%），再分别编码打包。
实测 pretrain_zh：19,500 / 198 / 198 篇；pretrain_en：2,897 / 29 / 29 篇。
Stage 7 的"行级 token 重叠检查"结果为 **0%**，验证划分没有泄漏。

## 4. Stage 4 原理：从零预训练

### 4.1 训练目标：自回归语言模型

模型把序列概率分解为条件概率乘积：

```
P(x_1…x_T) = Π_t P(x_t | x_<t)
```

训练就是最小化负对数似然（交叉熵）。Transformer 的因果注意力保证位置 t 只能看到 <t 的 token；
输入 `tokens[:-1]`、目标 `tokens[1:]`，一次前向就同时预测所有位置的 next token（teacher forcing）。

本课模型（decoder-only，17M/42M/110M 三档）组件与原理：

| 组件 | 作用 | 为什么现代模型用它 |
|---|---|---|
| 因果自注意力 | token 间信息交互 | 并行训练、推理时 KV cache |
| RoPE（旋转位置编码） | 注入位置信息 | 相对位置外推性更好，无额外参数 |
| RMSNorm（pre-norm） | 归一化 | 比 LayerNorm 便宜、训练稳定 |
| SwiGLU | FFN 激活 | 同等参数下表达力更强 |
| GQA（分组查询注意力） | 减少 KV 头数 | 推理省 KV cache（本课 S/M/L 用 MHA，Qwen3 用 GQA） |
| 词嵌入与输出共享 | 省参数 | 小模型里省 20–40% 参数 |

### 4.2 训练动力学：每个 trick 解决什么问题

| 技术 | 原理 | 本课实测/设置 |
|---|---|---|
| AdamW | 一阶矩 + 二阶矩自适应步长，解耦权重衰减 | β=(0.9,0.95)，wd=0.1 |
| warmup + cosine | 初期梯度方向不可靠，先小学习率热身，后期衰减收敛 | 自适应 warmup = min(100, 总步数/10)，实测 **48 / 16 / 6** 步 |
| 梯度裁剪 | 限制单步更新幅度，防梯度爆炸 | 1.0 |
| 梯度累积 | micro-batch 累加梯度再更新，等效大 batch | S: 8×1，M: 4×2，L: 2×4（乘 seq 长度） |
| 梯度检查点 | 不存中间激活，反向时重算，**计算换显存** | M/L 档开启 |
| 混合精度 | bf16 forward/backward + fp32 主权重 | 实测 bf16 autocast 可用 |
| 检查点/续训 | 保存模型+优化器+调度器+数据位置+RNG | 无状态批采样，续训只需全局 step |

**梯度累积的等价性**（重要且容易错）：一个优化器 step 处理的 token 数 =

```
tokens_per_step = batch_size × seq_len × grad_accum
```

实测验证：S 档 489 步 × (8×512×1) = **2,002,944** token；M 档 163 步 × 6144 = **1,001,472**；
L 档 62 步 × 8192 = **507,904**。与 summary 的 `tokens_seen` 完全一致——说明"无状态批采样 +
梯度累积"的实现是对的。

### 4.3 实测结果与"为什么 loss 是这样"

| 档位 | 参数量 | tokens/param | val loss | 有效算力 | 峰值显存 | tokens/s |
|---|---|---|---|---|---|---|
| S | 16.91M | 0.118 | **6.897** | 2.32 TFLOP/s | 4.23 GB | 20,023 |
| M | 41.69M | 0.024 | 7.924 | 2.05 TFLOP/s | 5.29 GB | 7,117 |
| L | 110.12M | 0.0046 | 8.192 | 2.27 TFLOP/s | 4.26 GB | 2,931 |

**不要用这张表得出"模型越大越差"的结论**：三档 token 预算不同（2M / 1M / 0.5M），
L 档只训了 0.51M token（0.0046 tokens/param），under-train 严重。规模律要求"同 token 预算
比较"，这正是 Stage 4 文档和本节反复强调的公平比较原则。在相同计算量包络里，三档的
有效算力相近（2.0–2.3 TFLOP/s），说明实现没有"大模型就变慢得离谱"的问题。

### 4.4 MLX 对照：两个框架为什么能做到数值几乎一致

MLX 是 Apple 的数组框架（惰性求值 + 统一内存），本课用同一套结构（参数名/形状一致）重建模型，
直接把 PyTorch `state_dict` 的权重拷进 MLX 模型，同一批数据、fp32 下比较：

| 指标 | 实测 | 含义 |
|---|---|---|
| loss 相对误差 | **0.0** | 前向计算一致 |
| logits 最大绝对误差 | 2.4e-6 | 浮点运算顺序差异（FP32 精度内） |
| 梯度范数相对误差 | 1.2e-7 | 反向传播一致 |
| MLX / MPS 训练吞吐 | 23,164 / 20,023 = **1.16×** | 同模型同配置实测 |

**原理结论**：两个框架的差异主要来自浮点累加顺序，不是算法差异；因此"MLX 是黑盒、不可信"
的担心在数值上不成立。吞吐差异则来自内核实现与图调度，会随模型/序列长度变化。

### 4.5 断点续训原理

训练状态 = 模型参数 + 优化器状态（Adam 的 m/v）+ 学习率调度器进度 + **数据位置** + RNG。
本课用"无状态批采样"：第 i 个 batch 由全局 batch 序号唯一确定（固定种子的随机置换），
所以续训只需恢复 `global_step`，数据位置自动对齐。单元测试验证了续训后 loss 与原始训练
同 step 一致（容差 5%）。

## 5. Stage 5 原理：指令微调与 LoRA

### 5.1 SFT 在优化什么

预训练模型学的是"互联网文本的分布"，SFT 把它变成"指令 → 回答"的条件分布：

```
SFT loss = - Σ_t log P(y_t | x, y_<t)     只对 assistant 回复的 token 求和
```

### 5.2 为什么必须做"损失掩码"

对话模板把 system/user/assistant 拼成一条序列。如果不加掩码，模型会同时学习"复述用户问题"
和"生成回答"，梯度被 prompt 主导（prompt 通常比回答长），模型会变得只会接话。

正确做法：prompt 部分的 label 置为 `-100`（PyTorch 的 ignore_index），只有 assistant 回复
计入损失。实测自检（`mask_check.json`）：

| 项目 | 实测 |
|---|---|
| prompt token 数 | 38（全部标记为不参与损失） |
| response token 数 | 7（参与损失） |
| prompt_masked | true |
| assistant 片段解码 | `"苹果@45"<|im_end|>`（含 EOS） |

### 5.3 LoRA：低秩假设与参数量公式

LoRA 假设微调时的权重更新是低秩的：`W' = W + BA`，其中 `B∈R^{d×r}`、`A∈R^{r×k}`，r ≪ d,k。
只训练 A、B（B 初始化为 0，所以训练开始时 W'=W，不破坏基座）。每个被适配的线性层增加
`r × (in_features + out_features)` 个参数。

用 Qwen3-0.6B 的真实形状（hidden=1024，28 层，16 头×head_dim=128，KV 头 8，FFN=3072）：

| 模块 | in → out | 每层 LoRA 参数（×r） |
|---|---|---|
| q_proj | 1024 → 2048 | 3,072r |
| k_proj | 1024 → 1024 | 2,048r |
| v_proj | 1024 → 1024 | 2,048r |
| o_proj | 2048 → 1024 | 3,072r |
| gate_proj | 1024 → 3072 | 4,096r |
| up_proj | 1024 → 3072 | 4,096r |
| down_proj | 3072 → 1024 | 4,096r |
| **每层合计** | | **22,528r** |

28 层 × 22,528 = **630,784r**：

- r=16 → **10,092,544** 参数 → 实测 **10,092,544**（完全一致）
- r=8 → **5,046,272** → 实测 **5,046,272**（完全一致）

LoRA 的显存收益来自"不保存基座模型的优化器状态"：全参训练 0.6B 需要 ~16N 字节状态，
LoRA 只需为 10M 可训练参数存 Adam 状态。但**激活值仍与全参训练一样大**——实测峰值仍达
20.9 GB（0.6B fp32 权重 + 激活 + MPS 缓存）。这是"LoRA 省显存"常被误解的地方。

### 5.4 为什么必须 fp32 主权重 + bf16 autocast（真实踩坑）

bf16 只有 8 位尾数（约 3 位十进制有效数字）。AdamW 的更新量 ≈ learning_rate × 梯度/二阶矩，
典型相对变化约 1e-4；把 1e-4 量级的更新直接加在 bf16 参数上，会被舍入丢失甚至引入偏差。
初版实现直接用 bf16 权重训练，实测 30 步内 loss 从 1.25 **升到** 3.0。

修复：**fp32 主权重 + autocast bf16 前向/反向**（标准 AMP）。固定批次 6 步：

```
lr=5e-5: loss 3.4297 → 3.3072 → 3.0770 → 2.8027 → 2.5509 → 2.2965   （稳定下降）
```

30 步 sanity 结果（初始验证损失 **2.798**，30 步后降到下表值——**sanity 档也确实在学，只是幅度有限**）：

| 变体 | 可训练参数 | 占比 | final train loss | val loss | tokens/s | 峰值显存 |
|---|---|---|---|---|---|---|
| lora_r16 | 10,092,544 | 1.67% | 2.166 | **2.342**（↓0.46） | 480 | 20.9 GB |
| lora_r8 | 5,046,272 | 0.84% | 2.171 | 2.345 | 617 | 20.9 GB |

r8 与 r16 在 30 步时效果几乎一样（数据/步数太少，容量差异体现不出来），但 r8 快约 29%——
这是"参数效率 vs 计算效率"的直观演示。

## 6. Stage 6 原理：偏好优化（DPO）

### 6.1 从 RLHF 到 DPO 的推导

标准 RLHF 分两步：先训练奖励模型 r(x,y)，再用 PPO 优化策略并加 KL 约束：

```
max_π E_{y~π}[ r(x,y) ] - β · KL(π || π_ref)
```

DPO 的关键洞察：这个约束优化问题的最优策略有闭式解

```
π*(y|x) ∝ π_ref(y|x) · exp( r(x,y) / β )
```

反解出隐式奖励 `r(x,y) = β log(π*/π_ref) + 常数`，再代入 Bradley-Terry 偏好模型
`P(chosen ≻ rejected) = σ(r_c - r_r)`，就得到只依赖策略/参考模型 logprob 的 DPO 损失：

```
L_DPO = - log σ( β [ (log π_θ(c) - log π_θ(r)) - (log π_ref(c) - log π_ref(r)) ] )
```

含义：**增大"优选回答相对劣选回答"的隐式奖励差，同时用参考模型锚住**——β 越大越贴近参考模型
（保守），越小越激进。参考模型通常是冻结的 SFT 模型。

### 6.2 实现正确性的"零信息检验"

当策略 = 参考模型时，括号内为 0，于是：

```
L = -log σ(0) = log 2 ≈ 0.6931
reward_margin = 0
accuracy = 0.5（随机）
KL = 0
```

实测 DPO 第一步：

| 指标 | 理论值 | 实测 |
|---|---|---|
| loss | 0.6931 | **0.693147** |
| reward margin | 0 | 1e-6 |
| accuracy | 0.5 | **0.5** |
| approx KL | 0 | 4.2e-5 |

**这是 DPO 实现最有效的单元检验**：任何符号错误、参考模型未冻结、mask 错位都会立刻破坏这些值。

### 6.3 实测结果与解读

| 项目 | 实测 |
|---|---|
| 偏好数据 | 公开 2,850 对（HH-RLHF 测试分片）+ self-play 3 对；验证 150 对 |
| β | 0.1 |
| 训练 | 20 步，batch 2 × grad_accum 2 |
| final train loss | 0.684 |
| eval loss / margin / accuracy | 0.695 / **-0.003** / 0.5 |
| 近似 KL | 0.10 |
| 峰值显存 | 13.4 GB（策略 + 参考两份 fp32 权重） |
| 监控状态 | ok（无过度优化告警） |

**原理解读**：20 步、学习率 5e-6 的训练量远远不足以让 0.6B 模型改变行为：
- margin 仍接近 0、accuracy=0.5 → 策略还没有真正偏好 chosen；
- KL=0.10 很小 → 与参考模型偏离有限；
- 这些都是**预期现象**，说明优化器在缓慢移动而不是崩掉。

### 6.4 过度优化（reward hacking）的原理与监控

DPO/RLHF 的经典失败模式：策略钻奖励的空子，margin 越来越高但生成质量下降。
本课用三个信号监控（`check_alignment_health`）：

1. **奖励间隔（margin）**：过大（>1.5 warn，>3.0 stop）说明过度优化；
2. **近似 KL**：与参考模型偏离过大（>2.0）说明跑偏；
3. **生成质量**：固定提示集生成的 distinct-1 相对基线下降 >30% 时告警。

原理：DPO 的"奖励"是隐式的，没有真实奖励模型兜底，所以**KL 与生成质量是唯一的安全绳**；
`stop_on_unhealthy=true` 时可自动中止并保存检查点。

## 7. Stage 7 原理：评测与实验追踪

### 7.1 困惑度：定义与可比性

PPL = exp(平均 CE loss)。它是"每 token 平均候选数"的几何平均。三个要点：

1. **必须按 token 加权**：先累加每个 token 的 CE，再除以总 token 数，最后 exp；
2. **不同分词器的 PPL 不可比**：词表越大，随机基线越高（16k→9.7，32k→10.4）；
3. **checkpoint / 数据子集不同也会变**：Stage 7 用各档 `best.pt` 并在 val 上分块评测，
   与 Stage 4 的最终 loss 有少量差异。

实测对照：

| 档位 | Stage 4 final val loss | exp 后 | Stage 7 实测 PPL | 差异原因 |
|---|---|---|---|---|
| S | 6.897 | 990 | 1000.8 | 用的是 best.pt + 分块评测 |
| M | 7.924 | 2,764 | 3,168.7 | 同上（best.pt 更早，欠训练） |
| L | 8.192 | 3,607 | 3,839.7 | 同上 |

**结论**：数量级一致（原理正确），具体数字的差异来自"哪个检查点、哪些 token"——评测必须
记录这些元信息，否则数字不可复现。

### 7.2 选择题评测：loglikelihood 评分

对每个选项计算"续写该选项"的**平均对数概率**，取最大者：

```
score(option) = (1/|o|) Σ_t log P(o_t | question, o_<t)
```

这是 lm-evaluation-harness 的通用做法，不需要模型会"输出格式"，只依赖语言模型本身。
随机基线 = 1/选项数 = 25%。实测 S/M/L 准确率 35% / 25% / 40%——**基本在随机水平附近**，
符合"欠训练小模型"的预期（见 0.2）。这不是评测代码的问题，而是模型能力的真实反映。

### 7.3 数据泄漏与可复现

- **泄漏检查**：对比 packed val 与 train 的行级 token 哈希，实测重叠 **0%**；
- **可复现**：固定种子 + 确定性评测，重复评测两次的 PPL 差异 **0.0**（容差 0.001），
  远小于 Stage 4 两次训练之间的差异（0.003–0.008，来自 MPS 非确定性）。

**原理**：评测的方差有两个来源——模型训练的不确定性（种子/并行）与评测采样。
固定种子能把评测方差压到 0，从而把观察到的差异归因于模型本身。

### 7.4 跨实验比较的公平性

Stage 7 的对比报告自动收集 Stage 4（规模/后端）、Stage 5（SFT 前后）、Stage 6（DPO 前后）的产物。
但**只有同 token 预算、同分词器、同评测集才能横比**——这正是 4.3 节强调的规模律比较原则。
本课报告的用途是"验证对比管线"，不是给模型排名。

## 8. Stage 8 原理：量化、推理与服务

### 8.1 量化的数学：仿射量化与 bits/weight

把浮点权重压成低比特整数（常见 affine/group-wise 量化，组大小 64）：

```
w ≈ s · (q - z)        q ∈ [0, 2^b - 1]
```

每个量化组要存一个 scale（和 zero point），所以实际每权重比特数 **略大于 b**。
MLX 转换日志实测：

| 配置 | 每权重比特数 | 理论体积（596M 参数） | 实测体积 |
|---|---|---|---|
| bf16 | 16 | 1.19 GB（权重本身） | 源模型目录 2.2 GB（SFT 合并时以 fp32 保存） |
| 8bit | **9.003** | 596M × 9.003/8 ≈ 0.671 GB | **0.635 GB** |
| 4bit | **5.003** | 596M × 5.003/8 ≈ 0.373 GB | **0.358 GB** |

体积账与实测吻合（差在 embedding/输出层可能不量化等细节）——这说明"量化体积 ≈
参数量 × bits/weight / 8"这个公式可以直接用来做预算。

### 8.2 为什么 4bit 能快 3 倍：推理是"访存密集"的

生成一个 token 时，模型必须把**全部权重读一遍**（矩阵乘的算术强度低，尤其 batch=1）。
所以推理速度上限由内存带宽决定：

```
tokens/s ≈ 内存带宽 / 每 token 需要读取的字节数
```

本机 M4 Pro 内存带宽约 273 GB/s；每 token 需读权重：

| 精度 | 每 token 权重字节 | 理论上限 | 实测 tokens/s | 实测/上限 |
|---|---|---|---|---|
| bf16 | 1.19 GB | 229 | 147–161 | 64%–70% |
| 8bit | 0.635 GB | 430 | 348.6 | 81% |
| 4bit | 0.358 GB | **763** | **521.3** | 68% |

**原理验证**：4bit 相对 bf16 的理论加速比 = 1.19 / 0.358 ≈ **3.33×**；实测 521 / 155 ≈ **3.4×**。
两者高度一致，证明"解码阶段是带宽受限"的判断正确，也解释了为什么量化在单机推理收益巨大。
（没达到 100% 上限是因为 KV cache、激活、采样等额外开销；batch>1 时会摊薄权重读取，又是另一笔账。）

### 8.3 TTFT 与吞吐：prefill vs decode

- **prefill（首 token 前）**：把整个 prompt 并行算一遍，是**计算密集**的；
- **decode（逐 token 生成）**：每步只算一个新 token，是**访存密集**的。

所以 TTFT 主要由 prompt 长度和芯片算力决定（实测 0.012–0.07 s），吞吐由带宽和量化决定。
长 prompt 时 TTFT 会更明显。生产调度（vLLM 的连续批处理、PagedAttention）本质上是在同时优化
这两段的显存/带宽利用，而本课的单机服务是"一次一个请求串行"的简化版。

### 8.4 服务原理：协议就是契约

OpenAI 兼容服务的价值在于**客户端生态**：任何支持该协议的客户端无需改代码即可切换到本地模型。
本课实测的契约检查：

| 检查 | 结果 |
|---|---|
| `GET /v1/models` | ✅ 200，返回 model list |
| 非流式 chat completion | ✅ `chat.completion` + choices/message |
| SSE 流式 | ✅ `chat.completion.chunk` + `[DONE]` |
| 非法请求（空 messages / temperature=5） | ✅ 400 + `invalid_request_error` |
| 并发请求 | ✅ 锁串行化后全部 200 |

**原理**：服务层要保证的是"输入校验、响应结构、流式分帧、错误语义"四件事；性能优化
（批处理、KV cache 复用、多副本）是另一层。本课把两层分开讲，避免"能起服务"和"能扛流量"混淆。
